# 蓝牙吊坠下位机开发工作小结 2026-06-06

## 1. 今日背景

今天主要讨论并调整了上位机通信方案。

之前的设计是：

- 吊坠之间使用扩展广播和扫描通信。
- 手机或 PC 上位机通过 BLE 连接 + GATT 调试服务和本机吊坠通信。

后来确认一个关键限制：当前 Telink B85m Single Connection SDK 没有明确支持“连接态下继续使用扩展广播 + 扫描”稳定共存。SDK 提供的连接态广播接口更接近 legacy advertising，广播数据会受到 31 字节限制，不适合继续承载当前较长的设备间协议帧。

因此今天决定调整设计：上位机通信也改为无连接广播扫描模式，统一使用 Extended Advertising 作为底层通信方式。

## 2. 今日完成的主要工作

### 2.1 新增广播上位机通信协议文档

新增文档：

```text
doc/蓝牙吊坠广播上位机通信协议.md
```

文档定义了新的通信分层：

```text
Extended Advertising Data
  -> Manufacturer Specific Data
    -> PENDANT-ADV frame
      -> HOST-ADV payload
        -> Host Command / Response / Log / Event
```

当前设计中，上位机命令、设备响应、日志、事件都通过扩展广播承载。

### 2.2 新增固件广播上位机通道

新增模块：

```text
tc_ble_single_sdk/vendor/ble_sample/pendant/host_adv/
```

核心文件：

```text
app_host_adv.h
app_host_adv.c
```

模块职责：

- 接收上位机通过扩展广播发来的 HOST-ADV 命令。
- 对 HOST-ADV 分片进行重组。
- 按 `Type + Seq + Cmd + TotalLen + CRC16` 做短时间去重，避免重复广播导致命令多次执行。
- 将完整命令投递给 `app_host_cmd_on_rx_message()`。
- 将设备响应、日志、事件封装为扩展广播 Data 帧发回上位机。

当前可靠性策略：

- 每个响应分片重复广播 3 次。
- 尚未实现 ACK、缺片重传和发送完成确认。

### 2.3 新增 Host 统一传输层

新增模块：

```text
tc_ble_single_sdk/vendor/ble_sample/pendant/host_transport/
```

核心文件：

```text
app_host_transport.h
app_host_transport.c
```

模块职责：

- 给 `app_host_cmd` 提供统一发送出口。
- 当前优先支持广播通道 `host_adv`。
- 保留 GATT 通道兼容能力，后续需要时可通过宏重新打开。

这样 `app_host_cmd` 不再直接依赖 `app_host_gatt`，后续上位机通道可以切换或并存。

### 2.4 修改 BLE 初始化策略

修改文件：

```text
tc_ble_single_sdk/vendor/ble_sample/app.c
```

主要变化：

- 默认 `APP_BLE_ENABLE_GATT_DEBUG = 0`。
- 默认 `APP_BLE_ENABLE_DISCOVERY_SCAN = 1`。
- 扩展广播从 connectable 改为 non-connectable。
- 默认开启扫描。
- 扫描 duplicate filter 改为关闭，便于 RSSI 算法和广播命令重复帧进入上层。

当前预期现象：

- 手机或 PC 不能再像以前一样连接 `PENDANT`，这是预期结果。
- 设备应持续对外发送扩展广播。
- 设备应持续扫描周围扩展广播。

### 2.5 修改广播调度器

修改文件：

```text
tc_ble_single_sdk/vendor/ble_sample/pendant/adv_scheduler/app_adv_scheduler.c
```

主要变化：

- 原来只有一个 pending frame。
- 现在改为 8 深度发送队列。
- 入队时复制 payload，避免临时栈数据失效。
- 队列有待发帧时使用较快的 50 ms 更新节奏。
- 空闲时继续周期性发送 Beacon。

### 2.6 修改扫描链路

修改文件：

```text
tc_ble_single_sdk/vendor/ble_sample/pendant/scan/app_scan.c
```

主要变化：

- Beacon 帧继续进入 `app_discovery_on_beacon()`。
- Data 帧额外进入 `app_host_adv_on_adv_frame()`。

后续设备间真正业务 Data 帧还需要接入 `peer_rx`，当前 Data 帧只有 HOST-ADV 被处理。

### 2.7 修改 Host 命令层

修改文件：

```text
tc_ble_single_sdk/vendor/ble_sample/pendant/host_cmd/app_host_cmd.*
```

主要变化：

- 新增 `app_host_cmd_on_rx_message()`，允许广播通道直接投递完整命令。
- 响应、日志、事件统一通过 `app_host_transport` 发送。
- 原有 GATT 分片入口 `app_host_cmd_on_rx_frame()` 保留，方便后续兼容。

### 2.8 新增 PC 侧协议辅助层

新增文件：

```text
pc_debug_tool/pendant_adv_protocol.py
```

功能：

- 编码和解析 `PENDANT-ADV` 扩展广播帧。
- 编码和解析 `HOST-ADV` payload。
- 能生成上位机广播命令帧，例如 `GET_DEVICE_INFO`。

注意：这只是协议辅助层，不是完整 PC 广播发送后端。

## 3. 当前最大数据量

当前各层数据限制如下：

| 层级 | 当前限制 |
| --- | ---: |
| 扩展广播总数据 | 240 字节 |
| `PENDANT-ADV` 单帧总长度 | 240 字节 |
| `PENDANT-ADV` Payload 最大长度 | 160 字节 |
| `HOST-ADV` Header 长度 | 14 字节 |
| `HOST-ADV` 单分片有效 Chunk | 146 字节 |
| 单条 Host Message | 192 字节 |

因此，当前上位机通道单次扩展广播中可承载的上位机有效数据是 146 字节；超过后会拆分为多个广播分片。

## 4. 今日讨论结论

### 4.1 是否必须使用 Python Bleak

结论：不必须。

之前使用 Python/Bleak 是因为 GATT 调试开发快。但切换到扩展广播上位机后，Bleak 不是最合适的底层。

Windows 上可继续评估：

- C# / C++ WinRT `BluetoothLEAdvertisementWatcher`
- C# / C++ WinRT `BluetoothLEAdvertisementPublisher`
- WinRT 的 `UseExtendedAdvertisement`

但实际能力取决于 Windows 版本、蓝牙适配器和驱动。

### 4.2 Windows 是否能直接使用 LL 层

普通 Windows 应用基本不能直接操作 BLE LL 层。

BLE LL 在控制器固件内部，普通应用最多通过系统蓝牙栈使用 GATT、扫描、广播等高层 API。Windows 内置蓝牙栈通常不会向普通用户态程序开放任意 HCI 命令发送能力。

### 4.3 更稳的上位机方案

如果 WinRT 扩展广播 API 限制太多，建议做一个 USB-BLE 广播网关：

- PC 工具通过串口、USB HID 或 WinUSB 和网关通信。
- 网关硬件负责 BLE 扩展广播发送和扫描。
- 网关可用 nRF52840、Telink 样板或其他 BLE SoC。

这是后续最稳的 PC 调试路线。

## 5. 当前 PC Debug Tool 状态

旧 `pc_debug_tool/app.py` 仍是 GATT 调试工具。

在当前默认固件配置下：

- 旧 PC Debug Tool 不能再连接设备。
- 因为固件默认关闭 GATT debug，并改为不可连接扩展广播。

如果临时需要恢复旧 PC 工具：

- 将 `APP_BLE_ENABLE_GATT_DEBUG` 改为 1。
- 重新编译固件。
- 旧 GATT Debug Service 理论上可继续使用。

但这会回到连接态限制，不适合后续统一广播通信方案。
