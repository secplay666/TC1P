# 蓝牙吊坠下位机开发工作小结 2026-06-21

## 1. 今日目标

今天继续验证两个 B85 吊坠在连接 PC 上位机的同时，是否还能稳定开启扩展广播和扩展扫描，并进一步推进：

- 双 GATT 连接下的 `adv1 + scan` 共存。
- B85 之间基于扩展广播的 P2P v2 可靠传输。
- PC A -> B85 A -> B85 B -> PC B 的正式聊天链路。
- 排查此前出现的复位、卡死、GATT shell 无响应问题。


收尾时已对 COM12、COM15 两块板执行串口软复位，并恢复为：

## 3. 今天做了什么

### 3.1 增加 BLE 诊断字段

扩展了 `radio` 输出，用于区分“正常断链”和“复位/卡死”：

- `conn_handle`
- `last_conn_handle`
- `conn_interval`
- `conn_latency`
- `conn_timeout`
- `last_disconnect_reason`
- `disconnect_count`
- `stop_count`

这个诊断很有用：后续多次确认 COM12 的问题不是普通断链，而是曾经出现过复位形态；后面又确认当前版本下 COM12 不再复位，而是 GATT/PC notify 响应路径异常。

### 3.2 改掉空闲 beacon 的高频更新

之前 `app_adv_scheduler_poll()` 在空闲 beacon 状态下也会周期性调用 `app_ble_update_ext_adv_data()`，实际会触发：

```text
disable adv1 -> setExtAdvData -> enable adv1
```

在“GATT 连接 + 扩展扫描 + 扩展广播”共存状态下，这个操作太重，容易触发异常。

现在策略改为：

- 空闲 beacon 只在初始化、显式 dirty、或者数据帧结束回退 beacon 时更新。
- 扩展广播控制器自己会重复发同一份 beacon，不再每隔一段时间重写。
- P2P 数据帧仍保留快速调度，避免牺牲数据发送能力。

验证结果：空闲 8 秒 `adv1 + scan` 共存时，芯片不再直接复位，`txstat build_ok=1` 也证明空闲 beacon 不再反复更新。

### 3.3 尝试把 P2P RX 从扫描事件路径延迟到主循环

发现正式聊天失败时，接收端容易在收到对端 DATA 扩展广播后异常。为降低 BLE controller event / HCI event 回调路径压力，增加了一个极小的 RX 延迟槽位：

- 扫描回调中只复制已解码的 DATA/ACK 帧。
- 真正的 `app_peer_transport_on_adv_frame()` 放到 `app_scan_poll()` 中执行。
- 队列只有 1 个槽位，满了直接丢帧，由 P2P v2 的 ACK/重传兜底。

中途遇到 RAM overflow，做了几项内存回收：

- `APP_HOST_ENABLE_ADV_TRANSPORT=0` 时，`host_adv` 编译为空实现，释放未使用的广播上位机传输缓存。
- 缩小 shell `sendmax` 调试 buffer。
- 将 shell 命令表从 26 项压到 20 项，临时不注册非关键命令：`beacon`、`send`、`sendmax`、`mac`、`rx`、`usb`。
- 修正 `app_scan_poll()` 中的大局部结构体，改成在延迟槽位原地处理，避免 200 字节级别对象压栈。

最终构建通过：

```text
text=133628
data=1140
bss=23052
bin=134964 bytes
```

## 4. 验证结果

### 4.1 通过的部分

两块板都能刷写、串口 shell 正常、PC 可扫描并连接。

空闲扩展广播共存方面，当前版本比之前明显好：

- 两块板能同时连接 PC。
- 两块板能执行 `ble adv1-on` 和 `ble scan-on`。
- COM12 串口最终显示 `conn=1 / adv1_en=1 / scan_en=1`，说明底层 radio 没有直接复位。
- COM12 能发现 COM15，`peers count=1`。

### 4.2 未通过的部分

8 秒双 GATT + `adv1 + scan` 测试仍未完全通过。

PC 侧现象：

```text
A: shell> peers
A: shell> radio
A: shell> p2pstat
```

A 端没有收到这些 shell 响应；B 端能正常响应。

但串口侧现象变了：

```text
COM12:
conn=1
adv1_en=1
scan_en=1
peers count=1
disc_n=0
```

这说明当前已经不是之前那种“芯片直接复位/跑飞”的状态。COM12 仍然活着，串口 shell 可用，radio 也在跑；问题更像是：

- GATT notify / response 没有回到 PC Bleak；
- 或者 PC 双连接 + B85 扩展扫描/广播共存时，某一路 GATT 通道进入了异常状态；
- 也可能是固件侧 GATT notify 队列、host transport 队列或连接事件调度被饿住。

正式 PC 聊天链路今天没有跑通。此前失败时能看到发送端已经发出 P2P 数据帧，但接收端/ACK 路径没有完整闭环。

## 5. 当前遗留问题

1. 双 GATT 连接 + 双板 `adv1 + scan` 运行 8 秒后，A 端 PC shell 响应丢失，但串口确认 A 端没有复位。
2. 需要继续确认是 PC/Bleak 双连接问题、B85 GATT notify 队列问题，还是 BLE controller 调度导致 GATT 通知无法及时发出。
3. P2P RX 延迟槽位是否真的改善 DATA 帧接收稳定性，还需要在 GATT 响应问题解决后继续验证。
4. 当前为节省 RAM，临时裁掉了一些非核心 shell 命令注册；后续需要整理成正式的调试配置开关。
5. `disc` 命令曾经不能让 COM12 立刻清掉 `conn=1`，这也是 GATT 状态机需要继续排查的线索。

## 6. 明天建议路线

建议先不要继续扩大功能，而是聚焦 GATT 响应丢失：

1. 在 `app_host_gatt_poll()`、host notify 队列、`app_host_transport_poll()` 加最小诊断计数，确认 shell 响应是否已经生成、是否入队、是否发送成功。
2. 修改 PC dual probe，避免依赖 notify 文本是否打印完整，改成记录每条 shell command 的 response timeout 和连接状态。
3. 做对照测试：
   - 只 A 开 `adv1 + scan`，B 只连接不扫。
   - A 开 `adv1`，B 开 `scan`，反过来再测。
   - 只保留一个 PC GATT 连接，另一块只串口控制，确认是不是 Windows/Bleak 双连接因素。
4. 如果确认是 GATT notify 被饿住，可以考虑降低扫描 duty cycle、增大连接 interval，或让 PC 调试时只连接一块板。
