# 微光产品板 OTA 调试工作小结 2026-07-12

## 调试目标

继续定位产品板 BLE OTA 失败的原因。重点不是重新设计 OTA，而是先确认失败发生在链路、GATT 回调、Telink `otaWrite()`、flash 写入还是 slot 启动切换。

## 当前硬件与基线

- 产品板可以通过 Telink 有线方式刷写，并能广播 `Glimmer`。
- 当前实测 BLE 地址：`A4:C1:38:19:A1:C8`。
- 当前诊断固件能通过 PC 调试通道读取设备信息。
- 当前临时版本号为 `APP_BUILD_VERSION_CODE=115`，这是调试用版本号，不代表正式版本规划。

一次成功读取到的关键设备信息：

- `fw_version_code=115`
- `ota_guard_state=1`，即 confirmed 状态
- `ota_active_slot=0`
- `ota_pending_slot=255`
- `ota_slot0_mark=75`
- `ota_slot1_mark=0`
- `ota_boot_config_status=0`
- `ota_configured_boot_addr=0x40000`
- `ota_program_boot_addr=0x40000`
- `ota_debug_write_count=0`

这说明当前启动地址配置已经生效，OTA 目标地址确认为 `0x40000`。

## 今天做过的实验

1. 重新编译并刷写当前诊断固件。
   - 编译通过。
   - 固件大小约 154 KB，在当前 `188 KB` OTA slot 限制内。
   - 产品板刷写后可以广播 `Glimmer`。

2. 做最小 OTA 写入实验：只发送 `START_EXT + DATA0`。
   - 用 PC/Bleak 找到 OTA characteristic。
   - characteristic 支持 `write`、`write-without-response`、`notify`、`read`。
   - `max_write_without_response_size` 实测为 80。
   - 发送后通过 Telink 直接读 `0x40000`，slot1 仍然没有固件数据。
   - 读到的 slot1 现象仍是：`0x40008=00`，其他大部分为 `FF`。

3. 排除“第一包太快”的可能。
   - `START_EXT` 后等待 `5s` 再发送 `DATA0`。
   - 结果仍然没有固件数据落到 `0x40000`。

4. 做 GATT OTA 回调 A/B。
   - 之前自定义 wrapper 会把 `rf_packet_att_t` 重新封装成 `rf_packet_att_data_t` 再交给 `otaWrite()`。
   - 今天临时改成直接把 OTA attribute callback 指向 `otaWrite`，与 SDK 旧 attribute table 的用法更接近。
   - 直连 `otaWrite` 后，`START_EXT + DATA0` 仍然没有写入 slot1。
   - 因此“wrapper 重新封包”不是唯一根因。

5. 准备了下一版诊断点。
   - 当前工作区最后状态是：OTA callback 不再重新封包，而是先记录 `debug_note_write()`，再把原始 `p` 传给 `otaWrite(conn_handle, p)`。
   - 这个版本已经编译并刷写过，但最后一次 `START+DATA0 + 读回计数` 被中断，尚未形成结论。

## 当前判断

基本可以暂时排除：

- OTA boot address 配置错误。
- slot1 地址选错。
- guard 立即回滚导致看不到数据。
- `START_EXT` 后第一包发送太快。
- 自定义 wrapper 重新封包作为唯一原因。

仍需继续确认：

- `DATA0` 是否真的进入了设备端 OTA characteristic callback。
- 如果已经进入 callback，是否被 Telink `otaWrite()` 因包格式、长度、状态流或 CRC 拒收。
- Windows BLE/Bleak 的 write-without-response 是否只是本地排队成功，并没有可靠送达设备。

## Windows BLE 现象

PC 端 Windows/Bleak 仍然不稳定，今天多次遇到：

- service discovery 超时；
- GATT characteristic discovery 被取消；
- 写入看似成功，但后续 GATT 读设备信息失败。

所以 PC 侧“进度百分比”不能直接当成设备端实际接收进度，必须用设备端计数或 Telink 读 flash 验证。

## 收尾整理状态

本次收尾前工作区有多处 OTA 相关改动，包含正式功能改动和临时诊断改动。整理后保留的重点包括：

- `tc_ble_multi_sdk/vendor/pendant/app_ota.c`
- `tc_ble_multi_sdk/vendor/pendant/app_ota.h`
- `tc_ble_multi_sdk/vendor/pendant/host_gatt/app_host_gatt.c`
- `tc_ble_multi_sdk/vendor/pendant/host_cmd/app_host_cmd.c`
- `pc_debug_tool/ota_update.py`
- `pc_debug_tool/pendant_protocol.py`
- `tools/build_pendant_multi.ps1`
- `tools/update_pendant_build_info.ps1`

整理原则：

- 保留 PC/Android 侧 write-with-response 方向，避免把 Windows/Bleak 或手机 BLE 栈的本地排队成功误判成设备端收到。
- 保留设备端 OTA guard/debug 字段，便于通过 `GET_DEVICE_INFO` 或 shell 判断 OTA 包是否进入设备回调。
- OTA 写入旁路诊断宏保持默认关闭，避免影响正常 OTA。
- 当前诊断版本为保证 B85 SRAM 链接通过，临时关闭 central/附近扫描；这会影响正式“附近发现”能力，后续需要单独做内存预算和功能拆分。
- 清理临时截图、UI dump 等与代码和调试结论无关的产物。

## 明天建议继续的顺序

1. 基于当前“原始 `p` 传给 `otaWrite` + debug 计数”的版本，重新跑最小实验：
   - 刷写；
   - 发送 `START_EXT + DATA0`；
   - 读 `GET_DEVICE_INFO`；
   - 看 `ota_debug_write_count` 和 `ota_debug_last_index`。

2. 根据计数分支判断：
   - 如果计数是 `1`，说明只收到 START，DATA 没进设备回调，重点查 Windows BLE 写入和 GATT characteristic。
   - 如果计数是 `2` 且 `last_index=0`，说明 DATA 已进回调，但 `otaWrite()` 没写 flash，重点查 Telink OTA 数据包格式和 `otaWrite()` 状态机。

3. 如果 PC 侧仍然不稳定，换 Android OTA 做对照。
   - Android BLE 栈比 Windows/Bleak 更适合验证 write-without-response 连续写入。

4. 必要时启用 SDK 默认 OTA service/group 做控制实验。
   - 目标是确认自定义 GATT 表是否和 Telink OTA server 有隐藏兼容性差异。

5. 最后清理调试代码。
   - 版本号恢复正常策略。
   - 临时 analog/debug counter 要么正式纳入诊断信息，要么移除。
   - guard abort/recovery 逻辑单独评估后再提交。
