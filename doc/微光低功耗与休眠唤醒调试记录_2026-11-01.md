# 微光产品板低功耗与休眠唤醒调试记录（2026-11-01）

## 本轮完成的内容

| 功能 | 状态 | 说明 |
| --- | --- | --- |
| BLE 低功耗（suspend） | ✅ | 广播间隙让 MCU 睡眠。OTA 期间、收到 App 命令后 1 秒内不睡；每次上电后保持 3 秒不睡，方便烧录器接管 |
| 连接期间睡眠 | ⏸ 默认关闭 | `PENDANT_BLE_PM_CONN_SLEEP=0`。开发板 B 开启后无法保持连接（只能广播）；产品板和开发板 A 开启后正常 |
| 空闲深度休眠 | ✅ | 满足以下条件持续 `PENDANT_IDLE_SLEEP_S`（300 秒）后休眠：无振动开关跳变、未连手机、未充电、附近无其他吊坠、不在 OTA |
| 唤醒源 | ✅ | 振动开关（按休眠时电平取反设置唤醒电平）、开始充电 |
| 唤醒前动作确认（毛刺过滤） | ❌ 未生效 | 详见下文“未解决问题 1” |
| 设备信息诊断字段 | ✅ | 空闲计数峰值、振动次数、唤醒源、阻止休眠原因、唤醒确认报告 |
| 烧录脚本 | ✅ | 对低功耗固件先复位再激活，确认 CPU 停住后再写入 |

## 产品板实测结果（v216~v227 测试固件，空闲时间临时改为 20/60 秒）

1. 空闲后进入深度休眠：多轮均正常，Swire 无法连接（深度休眠下 Swire 不可用属正常现象）。
2. 晃动 2~3 秒唤醒：正常。
3. 唤醒后放下再次休眠：正常。
4. 插 USB 唤醒，充电期间不休眠：正常。
5. 连接手机期间不休眠，断开后休眠：正常（见“未解决问题 2”）。
6. 敲一下：会唤醒（因为唤醒前确认未生效）。
7. 振动开关非常灵敏：持续晃动 4.5 秒约 550 次电平跳变。

## 修复的问题

- **引脚唤醒配置复位后不清除**：唤醒使能保存在模拟寄存器中，只有断电才会清除。休眠过一次后插上 USB，充电检测脚一直处于唤醒电平，BLE 每次 suspend 都被立即打断，导致不再广播，复位也无法恢复。现在每次启动都会先清除。
- **低功耗固件无法烧录**：Swire 无法停住处于 suspend 的 MCU。固件改为上电后保持 3 秒不睡，`flash_pendant_multi.ps1` 改为先复位、在窗口内激活并确认停住后再写入。
- **SDK 睡眠函数指针为空**：`cpu_sleep_wakeup` 在调用 `blc_pm_select_internal_32k_crystal()` 之前为 NULL，原有休眠路径一旦执行就会死机。

## 未解决问题

### 1. 深度休眠唤醒后无法识别唤醒来源，唤醒前确认没有执行

设计：引脚唤醒后先不开蓝牙，观察 2 秒，振动开关在至少 2 个不同的 100ms 时段内有跳变才视为真实转动，否则立即重新休眠，用于过滤敲击和毛刺。

要实现这一点，必须在启动时识别出“这是从我们的休眠中被唤醒”。已尝试以下方法，均不可靠：

| 方法 | 结果 |
| --- | --- |
| `pm_get_wakeup_src()` / `pm_is_deepPadWakeup()` | 真实引脚唤醒时为 0；普通复位时偶尔报 PAD |
| `DEEP_ANA_REG10` 写标记 | 深度休眠唤醒后丢失 |
| `DEEP_ANA_REG0` bit7 写标记 | 深度休眠唤醒后丢失 |
| `cpu_wakeup_init()` 之前读模拟寄存器 0x44 | 读数常常是无效值（两个寄存器读到同一个值）。SDK 进入 `cpu_wakeup_init` 时会先初始化模拟接口，且该函数本身并不读取 0x44 |
| 改用 `DEEPSLEEP_MODE_RET_SRAM_LOW32K` 并把标记放在 `.retention_data` | 标记仍丢失，说明当前配置下并没有真正进入 deep retention（休眠前已打开 `blc_pm_setDeepsleepRetentionEnable`，仍无效） |

测得的部分数据：Swire 复位后 0x44 读到 `0x82`，一次晃动唤醒读到 `0x8E`，但后续多次读到 `0x77`、`0xED` 这类无效值。

当前代码的实际行为：深度休眠唤醒后标记已丢失，走正常启动，相当于没有唤醒前确认，任何一次振动开关跳变都会唤醒设备。功能上安全（不会唤不醒，也不会误睡），代价是误唤醒时会多耗一次完整启动加空闲计时的电量。

后续可选方案：

- 自适应空闲时间：启动后第一段空闲只给 30 秒，检测到真实动作或连接过手机后恢复为 5 分钟。不需要识别唤醒原因。
- 硬件 RC 滤波：PC1 对地加 10~100nF 电容（已有 330k 上拉）。
- 按 SDK 官方方式启用 `PM_DEEPSLEEP_RETENTION_ENABLE`，需要评估保留区是否超过 32KB。
- 空闲时改用 suspend 代替深度休眠（内存不丢，可在内存中确认），代价是休眠电流高一个数量级。

### 2. App 被划掉后手机仍保持连接

在最近任务中划掉微光 App 后，吊坠仍处于被连接状态，只有关闭手机蓝牙才会断开。吊坠在被连接时不会休眠。需要 App 在退出或进入后台时主动断开连接。

### 3. 启动后一段时间内扫描不到或连接超时

烧录或唤醒后，PC 有时扫描不到产品板、连接超时；用 Swire 停住再恢复（`ac` + `rst -c`）后即恢复正常。出现时 `DEEP_ANA_REG0` 常带 SDK 的晶振启动异常标志（bit1）。可能与长期存在的“第一次连接容易超时”是同一问题，待排查。

### 4. 电池电压换算系数待校准

固件按开发板文档的分压比 0.784 换算。插着 USB 时固件读数约 3.6V；万用表空载测得 3.766V，两者不是同一状态，尚未校准。产品板有夹具，带电测量不便，可在改用稳压电源时校准。

## 调试注意事项

- 只在产品板上测试休眠唤醒：开发板没有振动开关和充电电路，PC1/PA0 悬空，会出现唤醒不了或反复唤醒。
- 板子深度休眠时 Swire 连不上；要刷写需先晃醒或插 USB，烧录脚本在启动后 3 秒窗口内完成激活。
- 唤醒刺激之后不要用 Swire 检查状态：`ac` 会停住正在做唤醒确认的 CPU，干扰测试结果。
- 测试休眠前先停掉手机 App，或关闭手机蓝牙。
- PC 蓝牙扫描偶尔失灵（扫描数为 0 或明显偏少），可用 `winrt.windows.devices.radios` 关闭再打开蓝牙恢复。
