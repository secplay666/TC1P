# 蓝牙吊坠下位机开发工作小结 2026-06-07

## 1. 今日目标

今天主要验证并修正一个关键问题：

在 B85 多连接 SDK 工程中，设备通过 GATT 连接 PC/手机上位机后，是否还能继续稳定运行扩展广播和扩展扫描。

这个能力是后续方案的核心基础：

- 手机/PC 上位机继续通过 GATT 调试、配置和查看状态。
- 吊坠之间继续通过扩展广播和扩展扫描发现、收发数据。
- 后续可在连接上位机时直接观察设备间互联状态，不再依赖多路串口。

## 2. 关键结论

当前已经验证通过：

- GATT 可以稳定连接。
- 连接状态下，扩展扫描仍持续收到广播报告。
- 连接状态下，扩展广播数据仍可持续更新。
- GATT 断开后，设备可以重新被 PC 扫描并再次连接。
- PC Debug Tool 使用的 GATT Debug Service 仍可用。

本轮调试确认：之前的问题不是 USB 引起的。USB 已先关闭，用来排除干扰。

## 3. 主要问题与原因

### 3.1 扫描 API 返回成功，但没有扫描报告

现象：

串口 `radio` 命令显示：

```text
adv0=0
adv1=0
scan=0
rpt_leg=0
rpt_ext=0
rpt_aux=0
```

说明扩展广告和扩展扫描接口都返回成功，但实际没有收到任何扫描报告。

原因：

原配置中：

```c
#define ACL_CENTRAL_MAX_NUM 0
```

虽然没有主动连接其他设备，但 Telink Multi Connection SDK 的扩展扫描调度实际需要 central 侧资源参与。`ACL_CENTRAL_MAX_NUM=0` 时，`blc_ll_setExtScanEnable()` 可以返回成功，但不会真正产生扫描报告。

修正：

```c
#define ACL_CENTRAL_MAX_NUM 1
#define ACL_PERIPHR_MAX_NUM 1
```

打开 1 路 central 资源后，扫描报告计数立即开始增长。

### 3.2 第一次 GATT 能连接，断开后再次连接超时

现象：

复位后第一次可以连接。断开后 PC 仍能扫描到 `PENDANT`，但再次连接一直超时。

原因：

`ADV_HANDLE0` 是 connectable advertising set。BLE 连接建立后，控制器会自动停止该 connectable advertising set。断开连接后，原代码只更新系统状态，没有重新启用 `ADV_HANDLE0`。

因此后续 PC 虽然能扫到设备，但扫到的是 `ADV_HANDLE1` 的非连接扩展广播，不能用于 GATT 连接。

修正：

在 `app_ble_on_disconnected()` 中，如果广播扫描流程仍处于启动状态，则重新 enable `ADV_HANDLE0`。

## 4. 当前固件配置

当前关键配置位于：

```text
tc_ble_multi_sdk/vendor/pendant/app_config.h
```

当前配置：

```c
#define ACL_CENTRAL_MAX_NUM                1
#define ACL_PERIPHR_MAX_NUM                1
#define PENDANT_USB_ENABLE                 0
#define PENDANT_EXT_ADV_ENABLE             1
#define APP_BLE_ENABLE_DISCOVERY_SCAN      1
#define APP_HOST_ENABLE_ADV_TRANSPORT      0
#define ACL_PERIPHR_SMP_ENABLE             0
#define ACL_CENTRAL_SMP_ENABLE             0
```

说明：

- USB 暂时关闭，避免继续干扰 BLE 共存验证。
- GATT Debug Service 保留。
- 上位机广播传输层暂时关闭。
- 扩展广播和扩展扫描开启。
- central/peripheral 各保留 1 路资源。
- SMP 关闭，避免配对流程影响调试。

## 5. 今日主要代码改动

### 5.1 BLE 初始化策略

文件：

```text
tc_ble_multi_sdk/vendor/pendant/app.c
```

主要调整：

- 使用扩展广播模块，不再同时初始化 legacy advertising 模块。
- 使用扩展扫描模块，不再同时初始化 legacy scanning 模块。
- `ADV_HANDLE0` 配置为 legacy connectable/scannable advertising，用于 GATT 连接。
- `ADV_HANDLE1` 配置为 extended non-connectable non-scannable advertising，用于吊坠业务广播。
- 配置扩展扫描参数，扫描 1M PHY。

在 GATT 断开后重新 enable `ADV_HANDLE0`，保证设备断开后仍可再次连接。

### 5.4 扫描报告计数

文件：

```text
tc_ble_multi_sdk/vendor/pendant/app.c
tc_ble_multi_sdk/vendor/pendant/app.h
```

新增计数：

- legacy advertising report 数量。
- extended advertising report 数量。

这些计数用于判断扩展扫描是否真的在工作。

### 5.5 串口 shell 增加 `radio` 命令

文件：

```text
tc_ble_multi_sdk/vendor/pendant/debug_shell/app_debug_shell.c
```

新增命令：

```text
radio
```

典型输出：

```text
[DBG] radio
 conn=1
 adv0=0
 adv1=0
 scan=0
 upd_st=0
 upd_ok=272
 upd_fail=0
 rpt_leg=91f
 rpt_ext=a0c
 rpt_aux=ed
```

其中：

- `conn=1` 表示 GATT 已连接。
- `adv0=0` 表示连接广告 handle 启动成功。
- `adv1=0` 表示业务扩展广播 handle 启动成功。
- `scan=0` 表示扩展扫描启动成功。
- `upd_fail=0` 表示扩展广播数据更新没有失败。
- `rpt_*` 持续增长表示扫描确实收到广播报告。

## 7. 当前遗留问题

### 7.1 USB 暂时关闭

当前：

```c
#define PENDANT_USB_ENABLE 0
```

所以 USB 下载/USB runtime 功能暂时不可用。后续如果要继续使用 USB 下载，需要单独做 USB 与 BLE 共存测试。

### 7.2 还没有验证双 B85 互相识别

目前已经证明：

- B85 可以在 GATT 连接状态下扫描到广播报告。
- 扩展扫描报告计数会增长。

但还没有进一步验证：

- 两个 B85 是否能互相收到对方的 `ADV_HANDLE1` 扩展广播。
- `app_scan` 是否能正确解析对方的业务 Beacon。
- `peer_table` 是否能正确生成邻近设备记录。
- RSSI 分级算法是否能按预期更新 S1/S2/S3。

这是下一步重点。

### 7.3 扩展广播业务协议仍需继续完成

当前重点是底层共存验证。后续还需要继续完善：

- 设备间业务 Data 帧收发。
- ACK/重传机制。
- 分片缓存。
- 发送队列。
- 上位机展示设备发现状态。

## 8. 明天建议继续顺序

1. 准备两块 B85 板子，都烧录当前最新固件。
2. 两块板子分别接串口，使用 `radio` 命令观察 `rpt_aux` 是否增长。
3. 使用 `peers` 命令查看是否有邻近设备记录。
4. 如果 `rpt_aux` 增长但 `peers` 为空，重点查 `app_scan` 对业务广播帧的解析。
5. 如果 `rpt_aux` 不增长，重点查 `ADV_HANDLE1` 广播参数、广播数据格式和扩展扫描 PHY。
6. 双板发现稳定后，再恢复 PC Debug Tool 页面上的邻近设备显示。
7. 最后再评估是否恢复 USB 下载功能，或者继续只用 EVK 烧录调试。

## 10. 总结

今天已经把最关键的技术风险压下去了：

Telink B85 Multi Connection SDK 在当前配置下，可以做到 GATT 连接、扩展广播、扩展扫描三者共存。

当前推荐继续走“手机上位机 GATT + 吊坠间扩展广播/扫描”的总体方案。相比全广播上位机方案，这条路对最终手机 App 更友好，也能保留成熟的 GATT 调试和配置通道。
