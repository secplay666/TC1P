# 蓝牙吊坠下位机开发工作小结 2026-06-07

## 1. 今日目标

今天主要继续调试两个 B85 吊坠之间基于 BLE 扩展广播的互联能力，目标是确认：

- 两块板子能否同时开启扩展广播和扩展扫描。
- 两块板子能否在 `scan + adv` 同时运行时互相发现。
- 两块板子能否通过扩展广播发送和接收 P2P 数据。
- 之前“一块板启动后另一块板容易卡死”的问题是否还能复现。

## 2. 关键结论

今天最终验证通过的方案是：

```text
B85 对 B85 通信：非可扫描扩展广播 ADV data + 扩展扫描
```

也就是：

- 发送侧使用 `blc_ll_setExtAdvData()` 更新 `ADV_HANDLE1` 数据。
- `ADV_HANDLE1` 使用 `ADV_EVT_PROP_EXTENDED_NON_CONNECTABLE_NON_SCANNABLE_UNDIRECTED`。
- 接收侧使用 extended scan 接收扩展广播报告。
- 两块板可以同时 `scan + adv`，并且能双向收发 P2P 测试数据。

今天确认：之前的“同时开扫描和广播后收不到对方数据”问题，主要发生在 scannable extended advertising + scan response 路径。改成 non-scannable extended advertising 后，两个 B85 之间的共存通信跑通。

## 3. 今日关键验证结果

### 3.1 Scannable scan response 路径的问题

之前尝试的方案是：

```text
ADV_HANDLE1 = extended scannable advertising
业务数据放在 extended scan response data
```

实测结果：

- 单板只广播、另一板只扫描时，可以收到 Beacon 和 DATA。
- 当发送端也同时开启 scan 时，外部设备收不到它的 scan response 数据。
- PC WinRT 扫描也收不到，说明不是 B85 接收端的问题，而是发送端在 `scan + scannable adv` 共存时 scan response 对外不可见或不稳定。

因此放弃把业务数据放在 extended scan response 的方案。

### 3.2 Non-scannable extended ADV data 路径验证通过

改为：

```text
ADV_HANDLE1 = extended non-connectable non-scannable advertising
业务数据放在 extended advertising data
```

验证结果：

- COM9 只广播，COM10 只扫描：COM10 能收到 COM9 Beacon。
- COM9 只广播，COM10 只扫描：COM10 能收到 COM9 `p2psend 13` DATA。
- COM9 同时 `scan + adv`，COM10 只扫描：COM10 能收到 COM9 Beacon 和 DATA。
- COM9、COM10 同时 `scan + adv`：双方能互相发现。
- COM9 -> COM10：`p2psend 13` 成功，接收端 `rx_accept > 0`。
- COM10 -> COM9：`p2psend 13` 成功，接收端 `rx_accept > 0`。
- 双板共存烟测约 10 秒后，两边 shell 均可 `ping`，没有复现卡死。

## 4. 当前 payload 限制

当前应用广播帧最大值暂定为：

```c
#define APP_ADV_FRAME_MAX_LEN 79
```

原因是当前 B85-to-B85 extended scan report 路径中，实测应用层稳定拿到的完整数据长度为 `0x4F = 79` 字节。

当前层级开销：

```text
APP_ADV_FRAME_MAX_LEN      = 79
BLE AD overhead            = 4
Pendant ADV header         = 50
Pendant frame CRC32        = 4
ADV frame payload max      = 79 - 4 - 50 - 4 = 21
P2P transport header       = 8
P2P user payload max       = 21 - 8 = 13
```

所以当前 shell 中看到：

```text
adv_max=4f
payload_max=15
p2pstat max=d
```

这不是 BLE 扩展广播的理论上限，而是当前 SDK 配置和 B85 扫描报告路径下已经验证稳定的保守上限。

## 5. 今日主要代码调整

### 5.1 `app_ble.c`

文件：

```text
tc_ble_multi_sdk/vendor/pendant/ble/app_ble.c
```

主要调整：

- `ADV_HANDLE1` 改为非可扫描扩展广播。
- 扩展广播数据更新改为 `blc_ll_setExtAdvData()`。
- 扩展扫描改为 active scan。
- 关闭 duplicate filter，避免动态广播内容被控制器过滤。
- 扫描开启方式改为 continuous scan。
- `ble adv1-on` 做成幂等，重复执行时不再重新配置并破坏状态。

### 5.2 `app.c`

文件：

```text
tc_ble_multi_sdk/vendor/pendant/app.c
```

主要调整：

- `ADV_HANDLE1` 初始化为 `ADV_EVT_PROP_EXTENDED_NON_CONNECTABLE_NON_SCANNABLE_UNDIRECTED`。
- `ADV_HANDLE1` 初始数据使用 `blc_ll_setExtAdvData()`。
- `APP_MAX_LENGTH_ADV_DATA` 设置为 80，匹配当前 79 字节应用帧。
- `APP_MAX_LENGTH_SCAN_RESPONSE_DATA` 收回到 31，因为当前业务链路不再依赖 scan response。
- 保留扩展扫描报告统计字段，用于 `radio` 命令查看 `rpt_ext/rpt_aux/aux_len/aux_max`。

### 5.3 `app_types.h`

文件：

```text
tc_ble_multi_sdk/vendor/pendant/common/app_types.h
```

主要调整：

```c
#define APP_ADV_FRAME_MAX_LEN 79
```

并补充注释说明：这是当前 B85-to-B85 已验证的稳定接收上限，不是 BLE 规范上限。

## 7. 当前已知问题

### 7.1 P2P 用户 payload 当前只有 13 字节

这是当前最明显的限制。后续需要继续查：

- B85 extended scan report 是否可以通过 SDK buffer 配置提高上限。
- 是否可以稳定接收 80 字节以上的 non-scannable extended ADV data。
- 如果底层上限无法提高，需要实现应用层分片和重组。

### 7.2 两块板的身份信息仍然重复

今天读到两块板的 `short_id` 和 EID 前几个字节仍然相同：

```text
short=120b0100
eid0=0
eid1=1
eid2=b
eid3=12
```

两块板 BLE MAC 不同，但身份模块里的唯一身份还需要后续重新写入不同 ID。否则后续做 peer table、定向消息和真实产品发现时会混淆。

### 7.3 COM9 与 COM10 固件版本状态

今天最后：

- COM10 已刷到最新收尾版，build time 为 `21:53:16`。
- COM9 是同通信逻辑的上一版，差异主要是收回 scan response buffer 和注释。

如果明天要继续做严格对比，建议先把 Telink 换回 COM9，再刷一次最新固件，让两块板完全一致。

## 9. 今日总结

今天把最关键的底层链路跑通了：

```text
两个 B85 同时扫描 + 同时扩展广播 + 双向 P2P 测试数据收发
```

当前推荐后续继续基于：

```text
non-scannable extended advertising data
```

作为吊坠之间的底层通信方式。相比 scan response 方案，这条路径在 B85-to-B85 共存测试中更稳定，已经通过双板互发验证。
