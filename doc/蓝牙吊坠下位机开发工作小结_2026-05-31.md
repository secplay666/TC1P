## 3. 当前设备发现问题分析

今天最后检查了两个设备互相发现失败的问题。

结论：当前代码状态下，两个设备都连接上位机时，不能互相发现是预期结果，因为扫描和连接态广播/扫描共存还没有真正启用。

### 3.1 当前广播机制

当前设备会周期性更新扩展广播数据：

- BLE Flags。
- 名称 `PENDANT`。
- 厂商自定义数据 `0xFF`。
- 自定义 `app_adv_proto` 帧。
- 帧内包含 EID、设备状态、电量、peer_count 等。

广播由 `app_adv_scheduler_poll()` 定期调用 `app_ble_update_ext_adv_data()` 更新。

### 3.2 当前扫描机制

扫描代码路径已经存在：

```text
controller_event_callback()
  -> app_pendant_on_adv_report()
  -> app_ble_on_adv_report()
  -> app_scan_on_report()
  -> app_adv_proto_decode()
  -> app_discovery_on_beacon()
  -> app_peer_table_find_or_alloc()
```

但当前宏默认关闭：

```c
#define APP_BLE_ENABLE_DISCOVERY_SCAN 0
```

因此 `app_ble_start_adv_scan()` 实际只开启扩展广播，没有开启扫描。

### 3.3 连接状态下的限制

即便打开扫描，当前连接事件里也会关闭扫描，断开连接后才重新打开。

目前还没有接入：

- `blc_ll_addScanningInConnSlaveRole()`
- `blc_ll_addAdvertisingInConnSlaveRole()`
- `blc_ll_setAdvParamInConnSlaveRole()`

因此“连接上位机时继续扫描其他吊坠，同时继续对外广播吊坠发现帧”还没完成。

## 4. 重要遗留问题

### 4.1 设备互发现

下一步应优先做互发现链路验证。

建议分两步：

1. 非连接状态互扫：
   - 打开 `APP_BLE_ENABLE_DISCOVERY_SCAN`。
   - 启用 `blc_ll_addScanningInAdvState()`。
   - 不连接 PC 上位机，只让两块板靠近。
   - 通过串口或 PC 单独连接其中一台读取 peer table。

2. 连接状态互扫和广播：
   - 接入 `blc_ll_addScanningInConnSlaveRole()`。
   - 接入连接态广播能力。
   - 评估连接态是否只能使用 legacy advertising。
   - 如果连接态广播无法承载当前完整扩展广播帧，需要设计一套精简发现广播格式。

### 4.2 扩展广播与连接态广播的取舍

当前设备间 Beacon 使用扩展广播，数据较长。

Telink SDK 中连接态广播接口看起来偏 legacy advertising，legacy 广播有效数据最多 31 字节。后续需要确认：

- 连接态是否支持扩展广播。
- 如果不支持，连接态发现帧需要压缩到 31 字节以内。
- 是否需要同时维护“扩展广播完整帧”和“连接态短发现帧”两套格式。

### 4.3 AES 仍是占位实现

当前 `app_crypto_aes128_encrypt()` 仍是 XOR 占位逻辑，不是真正 AES-128。

后续必须替换为真实 AES-128，否则：

- EID 不具备实际隐私保护能力。
- 从广播中能看出开发 key 痕迹。
- 唯一识别码派生机制不符合系统需求。

### 4.4 量产安全策略未定版

当前身份锁定是软件锁定。

量产前还需要确定：

- 正式固件是否禁用 `WRITE_IDENTITY`。
- 是否需要产测授权码。
- 是否区分产测固件和正式固件。
- 是否启用 Flash 写保护。
- 是否关闭 `APP_IDENTITY_ALLOW_DEV_FALLBACK`。
- 数据库记录如何备份、防重复、防误删。

### 4.5 自动烧录序号上限

当前 `terminal_sn` 格式为 `0xyymmddss`，其中 `ss` 只有两位十六进制/十进制样式空间。

目前工具限定 `01` 到 `99`。如果一天超过 99 台，需要重新定义终端序列字段，例如：

- 改为 `0xyymmnnnn`。
- 或将日期和流水号拆到不同字段。
- 或让 random 字段承担更多唯一性，但终端序列不再代表严格流水。

### 4.6 工厂自检还是框架

`RUN_FACTORY_TEST` 当前只是框架命令，返回值直接等于请求 mask。

后续需要逐步接入：

- 马达测试。
- 电池电压测试。
- 充电状态测试。
- Flash 读写测试。
- 广播测试。
- 扫描测试。

可以先用 PC 工具读取以下信息：

- `GET_FLASH_MAP`：确认 Flash 分区仍正确。
- `GET_IDENTITY`：确认设备是 `DEV_FALLBACK` 还是 `PRESENT|VALID`。
- `GET_FACTORY_INFO`：确认 Factory Record 是否已记录写入次数。
- `GET_PEER_TABLE`：确认互发现阶段是否有 peer。

如果互发现仍为空，优先检查：

- `APP_BLE_ENABLE_DISCOVERY_SCAN` 是否为 1。
- 是否调用 `blc_ll_setScanEnable(BLC_SCAN_ENABLE, ...)`。
- 是否收到 HCI advertising report。
- `app_adv_proto_decode()` 是否返回 `APP_OK`。
- 对端 EID 是否和本机不同。
- RSSI 是否达到默认阈值 `T1=-80`。
