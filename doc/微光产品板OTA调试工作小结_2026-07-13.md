# 微光产品板 OTA 调试工作小结（2026-07-13）

## 当前背景

本轮继续分析产品板 OTA 失败问题。之前已经确认：

- 产品板可以通过 Telink 直接刷写并运行新固件。
- B85 开发板 OTA 流程基本可用。
- 产品板 OTA 的主要失败现象不是单纯传输过程中丢包，而是 OTA 成功写入后，设备重启后不再广播。
- 通过 BDT 读 flash 对比发现，slot0 和 slot1 的 boot mark 都被清成 `0x00`，导致启动选择没有有效镜像。

本轮调试目标是验证“OTA 成功后补写目标 slot boot mark”的修复思路。

## 本轮已做的事情

1. 检查当前仓库状态和 OTA boot mark 修复代码。

   关键修改位于：

   - `tc_ble_multi_sdk/vendor/pendant/app_ota.c`
   - `pc_debug_tool/ota_update.py`
   - `android_glimmer_app/app/src/main/java/com/glimmer/app/GlimmerBleClient.java`

   其中 `app_ota.c` 里新增了 `app_ota_rewrite_slot_boot_mark()`，尝试在 OTA result success 回调里：

   - 备份目标 slot 首扇区；
   - 擦除目标 slot 首扇区；
   - 重写首扇区，并把 `BOOT_MARK_ADDR` 写成 `BOOT_MARK_VALUE`；
   - 清掉另一个 slot 的 boot mark；
   - 保存 OTA snapshot，便于后续读取诊断信息。

2. 编译生成 v124 测试固件。

   命令：

   ```powershell
   powershell -ExecutionPolicy Bypass -File .\tools\build_pendant_multi.ps1 -VersionCode 124
   .\pc_debug_tool\.venv\Scripts\python.exe .\tools\make_glimmer_ota_package.py --bin .\tc_ble_multi_sdk\build\B85\pendant\pendant.bin --out .\artifacts\pendant_product_ota_124_bootmark_fix.glimmerota --version-code 124 --private-key .\artifacts\glimmer_ota_private_dev2.pem
   ```

   结果：

   - 编译通过。
   - 生成 `artifacts/pendant_product_ota_124_bootmark_fix.glimmerota`。
   - bin 大小：`147732` bytes。

3. 旧固件运行状态检查。

   用户已全片擦除并刷写旧固件，板子可以运行。但通过 PC BLE 扫描没有稳定看到 `Glimmer` 或 `HHCCHH`。

   执行 Telink `active` 和 `reset` 后仍没有看到旧固件目标广播。因此本轮没有继续用最老固件作为 OTA 起点，而是改为先用 Telink 刷入可控的 v124 作为基线。

4. Telink 直接刷入 v124 基线。

   命令：

   ```powershell
   powershell -ExecutionPolicy Bypass -File .\tools\flash_pendant_multi.ps1 -DeviceId 1 -BinPath .\tc_ble_multi_sdk\build\B85\pendant\pendant.bin
   ```

   结果：

   - 刷写成功。
   - 复位后 BLE 扫描可以看到：

     ```text
     A4:C1:38:7E:E4:30 rssi=-57 name=Glimmer
     ```

   说明产品板运行当前新固件本身没有问题。

5. 编译生成 v125 OTA 包。

   命令：

   ```powershell
   powershell -ExecutionPolicy Bypass -File .\tools\build_pendant_multi.ps1 -VersionCode 125
   .\pc_debug_tool\.venv\Scripts\python.exe .\tools\make_glimmer_ota_package.py --bin .\tc_ble_multi_sdk\build\B85\pendant\pendant.bin --out .\artifacts\pendant_product_ota_125_bootmark_fix.glimmerota --version-code 125 --private-key .\artifacts\glimmer_ota_private_dev2.pem
   ```

   结果：

   - 编译通过。
   - 生成 `artifacts/pendant_product_ota_125_bootmark_fix.glimmerota`。
   - bin 大小：`147732` bytes。

6. 增强 PC OTA 工具的连接诊断。

   在 `pc_debug_tool/ota_update.py` 中增加：

   - BLE 连接超时参数 `--connect-timeout-s`；
   - 普通异常时打印异常类型和 `repr`；
   - 普通异常也按 `--connect-retries` 重试，而不是第一次失败就退出。

   语法检查通过：

   ```powershell
   .\.venv\Scripts\python.exe -m py_compile .\ota_update.py
   ```

7. 执行 v124 -> v125 OTA 测试。

   第一次 OTA 连接尝试：

   ```powershell
   .\.venv\Scripts\python.exe .\ota_update.py --bin ..\artifacts\pendant_product_ota_125_bootmark_fix.glimmerota --address A4:C1:38:7E:E4:30 --pdu-len 64 --index-mode packet --write-response --pace-ms 0 --connect-retries 4 --connect-timeout-s 30 --current-version-code 124
   ```

   现象：

   - 第一次尝试没有进入 OTA 数据传输阶段。
   - 随后扫描不到 `Glimmer`。
   - Telink reset 后 `Glimmer` 恢复广播。

   第二次 OTA 尝试：

   - OTA 已进入数据发送阶段。
   - 由于外层命令超时时间约 5 分钟，进程在发送过程中被工具层杀掉。
   - Python 在 stdout 被关闭后抛出：

     ```text
     OSError: [Errno 22] Invalid argument
     ```

   这个错误来自调试进程输出流被关闭，不是下位机返回的 OTA 错误。

   中断后扫描不到 `Glimmer`。随后已执行 Telink reset，但最后一次复扫被用户打断，尚未确认 reset 后是否已经恢复广播。

## 当前结论

1. 产品板不是不能运行当前新固件。

   v124 通过 Telink 直接刷入后可以正常广播 `Glimmer`，地址为：

   ```text
   A4:C1:38:7E:E4:30
   ```

2. OTA 传输层之前已经被证明可以完整写入。

   此前 v122 -> v123 测试中，PC OTA 工具收到了 `result=SUCCESS`。后续 BDT dump 显示 slot1 内容和 OTA 包基本一致，说明数据落盘不是主要问题。

3. 当前最关键的疑点仍然是 boot mark。

   此前失败后的 flash 证据显示：

   - slot0 offset `0x08`：`0x00`
   - slot1 offset `0x08`：`0x00`

   这意味着 OTA 成功后没有留下一个有效启动 slot。

4. 本轮新增的 boot mark 补写修复已经能编译，但还没有完成闭环验证。

   原因是本轮 v124 -> v125 OTA 被外层工具超时中断，尚未跑到完整 OTA_END + result + 重启 + 扫描确认阶段。

5. 当前还不能下最终结论：boot mark 补写能不能解决产品板 OTA 后不广播。

   需要明天继续跑一次完整 OTA，外层命令超时要放长，避免在数据发送阶段被调试工具杀掉。

## 当前风险和注意事项

- 当前 `tc_ble_multi_sdk/build/B85/pendant/pendant.bin` 是 v125 构建产物。
- 产品板 slot0 之前通过 Telink 刷入的是 v124。
- v125 OTA 可能已经部分写入 slot1，但没有确认是否完成。
- 最后已执行 Telink reset，但 reset 后是否恢复广播没有完成复扫确认。
- 仓库有大量未提交修改，包含 OTA、App、PC 工具和文档相关改动；本次没有 commit。
- 根目录还有临时诊断文件：

  - `.tmp_ota_obj/`
  - `slot0_dump.bin`
  - `slot1_dump.bin`

## 明天建议继续的步骤

1. 先确认当前板子是否广播。

   ```powershell
   .\pc_debug_tool\.venv\Scripts\python.exe .\pc_debug_tool\raw_scan.py
   ```

2. 如果没有广播，先 Telink reset。

   ```powershell
   powershell -ExecutionPolicy Bypass -File .\tools\reset_pendant_multi.ps1 -DeviceId 1
   ```

3. 如果 reset 后仍无广播，读取两个 slot boot mark。

   ```powershell
   $bdt='C:\TelinkIoTStudio\tools\TBD_release\config\Cmd_download_tool.exe'
   & $bdt 1 B85 ac
   & $bdt 1 B85 rf 0 -s 64
   & $bdt 1 B85 rf 0x40000 -s 64
   ```

4. 如需恢复基线，重新 Telink 刷入 v124 或当前 v125。

   当前 v125 可直接刷：

   ```powershell
   powershell -ExecutionPolicy Bypass -File .\tools\flash_pendant_multi.ps1 -DeviceId 1 -BinPath .\tc_ble_multi_sdk\build\B85\pendant\pendant.bin
   ```

   如果需要重新做 v124 -> v125，需要先重新构建 v124 并刷入。

5. 完整 OTA 复测时，外层命令超时建议至少 10 分钟。

   ```powershell
   cd pc_debug_tool
   .\.venv\Scripts\python.exe .\ota_update.py --bin ..\artifacts\pendant_product_ota_125_bootmark_fix.glimmerota --address A4:C1:38:7E:E4:30 --pdu-len 64 --index-mode packet --write-response --pace-ms 0 --connect-retries 4 --connect-timeout-s 30 --current-version-code 124
   ```

6. OTA 完成后重点确认：

   - 是否收到 `result=SUCCESS`；
   - 是否重新广播 `Glimmer`；
   - 设备信息里的 `fw_version_code` 是否变为 `125`；
   - `ota_active_slot` 是否为目标 slot；
   - `ota_slot0_mark` 和 `ota_slot1_mark` 是否只有一个为 `0x4B`；
   - 如果失败，立刻通过 BDT 读取 `0x00000` 和 `0x40000` 前 64 字节。
