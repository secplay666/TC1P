# 微光大对象传输协议第一版

日期：2026-06-28

## 目标

第一版用于验证 Glimmer 终端之间传输图片或较大文件的可行性。设计重点不是最终 UI，而是先打通可压测、可修复、可继续演进的对象传输内核。

当前实现采用 App 层对象传输状态机，B85 终端只做透明 P2P 转发：

- Android App 负责对象分片、缺片统计、重传修复、CRC 校验。
- B85 负责把文件帧作为 `APP_PEER_MSG_FILE` 广播给对端。
- 对端 App 负责组包，并通过同一 P2P 文件通道回传 REPORT/DONE。

## Host 与 P2P 通道

固件新增：

- P2P 消息类型：`APP_PEER_MSG_FILE = 3`
- Host 命令：`HOST_CMD_P2P_FILE_SEND = 0x15`
- Host 事件：`HOST_EVENT_P2P_FILE = 0x86`

发送方向：

```text
App A
  -> HOST_CMD_P2P_FILE_SEND
  -> B85 A
  -> APP_PEER_MSG_FILE
  -> B85 B
  -> HOST_EVENT_P2P_FILE
  -> App B
```

确认与缺片修复方向完全对称。

固件侧发送命令必须进入 `app_host_cmd_poll()` 后再调用 P2P 发送接口，不能在 GATT 命令处理回调里直接发送。这个约束来自 BLE/GATT 与扩展广播并发时的稳定性问题。

## 文件帧格式

所有文件帧都有 8 字节公共头：

| 字段 | 长度 | 说明 |
| --- | ---: | --- |
| magic | 2 | 固定 `GF` |
| version | 1 | 当前为 `1` |
| type | 1 | 帧类型 |
| file_id | 4 | 本次对象传输 ID |

### START

| 字段 | 长度 | 说明 |
| --- | ---: | --- |
| 公共头 | 8 | `type=1` |
| total_len | 4 | 对象总长度 |
| chunk_size | 2 | DATA 分片载荷长度 |
| total_chunks | 2 | 总分片数 |
| crc32 | 4 | 完整对象 CRC32 |
| flags | 1 | 预留 |

### DATA

| 字段 | 长度 | 说明 |
| --- | ---: | --- |
| 公共头 | 8 | `type=2` |
| chunk_index | 2 | 分片序号 |
| data | N | 分片数据 |

### REPORT

| 字段 | 长度 | 说明 |
| --- | ---: | --- |
| 公共头 | 8 | `type=3` |
| total_chunks | 2 | 总分片数 |
| received_count | 2 | 已收到分片数 |
| bitmap_base | 2 | 当前第一版固定为 0 |
| bitmap_len | 1 | 缺片 bitmap 字节数 |
| missing_bitmap | N | bit=1 表示该分片缺失 |

### DONE

| 字段 | 长度 | 说明 |
| --- | ---: | --- |
| 公共头 | 8 | `type=4` |
| status | 1 | `0` 表示成功 |
| total_len | 4 | 对象总长度 |
| crc32 | 4 | 接收端计算出的 CRC32 |

### CANCEL

`type=5`，当前预留。

## 第一版限制

当前参数偏保守：

- 默认分片载荷：48 bytes
- 单对象上限：16 KB
- 最大分片数：384
- 发送间隔：60 ms
- REPORT 超时：8 s
- watchdog 整体重发上限：3 次
- repair round 上限：8 次

48 bytes 不是协议理论上限，而是为了避开当前 B85 到 App 的 GATT notify 队列、手机 BLE 写入节奏、扩展广播竞争带来的不稳定。后续可以在这个基线上逐步提高 chunk/window。

## 验证结果

测试环境：

- Pixel：`47162DLAQ003JV`
- Huawei/HarmonyOS：`2KE0219A22011091`
- Pixel -> Huawei 目标 short id：`C4C4154A`
- Huawei -> Pixel 目标 short id：`6B463997`
- chunk：48 bytes

已通过用例：

| 方向 | 大小 | 人工丢片 | 结果 |
| --- | ---: | --- | --- |
| Pixel -> Huawei | 1 KB | 无 | 通过 |
| Pixel -> Huawei | 4 KB | 无 | 通过 |
| Pixel -> Huawei | 8 KB | 无 | 通过 |
| Pixel -> Huawei | 4 KB | 每 7 片跳过 1 片 | 通过 |
| Huawei -> Pixel | 1 KB | 无 | 通过 |

测试脚本：

```powershell
powershell -ExecutionPolicy Bypass -File .\tools\test_glimmer_file_transfer.ps1 `
  -SenderDevice 47162DLAQ003JV `
  -ReceiverDevice 2KE0219A22011091 `
  -TargetShortId C4C4154A `
  -Size 4096 `
  -Chunk 48 `
  -DropEvery 7
```

## 后续方向

下一步建议按顺序做：

1. 接入真实图片/文件选择 UI，并先限定小图或压缩图。
2. 发送前对完整对象加密，再分片发送。
3. REPORT 支持 bitmap 分页，解除单个 REPORT 对最大分片数的限制。
4. 引入对象级传输队列，避免多个文件传输并发互相覆盖状态。
5. 在稳定后提高 chunk 或发送窗口，做吞吐优化。
