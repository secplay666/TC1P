# 微光个人对话加密设计

## 当前版本

当前实现为 `Chat Crypto v1`，加密发生在 B85 终端的个人对话业务层：

1. 手机 App 仍通过 `HOST_CMD_P2P_CHAT_SEND` 向本机 Glimmer 终端发送明文。
2. 本机 B85 在交给 P2P v2 可靠传输前，将聊天文本封装为加密载荷。
3. 对端 B85 收到 P2P v2 完整消息后，先解密并校验，再通过 `HOST_EVENT_P2P_CHAT` 上报给对端手机 App。
4. P2P v2 的分片、ACK、重传、超时、TX 失败事件保持不变。

这版主要目标是避免个人聊天明文直接出现在 BLE 扩展广播载荷中。

## 载荷格式

加密载荷头长度为 12 字节：

| Offset | 字段 | 长度 | 说明 |
|---:|---|---:|---|
| 0 | Magic | 2 | 固定为 `GC` |
| 2 | Version | 1 | 当前为 `1` |
| 3 | Flags | 1 | bit0 表示 encrypted |
| 4 | Nonce | 4 | 每条消息变化，混入 tick、随机数、短 ID 和本地计数 |
| 8 | Plain Length | 2 | 明文长度 |
| 10 | CRC16 | 2 | 明文 CRC16，用于解密后校验 |
| 12 | Ciphertext | N | AES-128 CTR 密文 |

当前个人对话明文上限为 184 字节，原因是手机事件帧最大 192 字节，聊天事件头占 8 字节。加密后进入 P2P 层的长度为 `明文长度 + 12`，最大为 196 字节，仍由 P2P v2 分片可靠传输承载。

## 密钥派生

当前版本使用产品固定密钥作为根密钥，并结合本机 EID、对端 EID 和 nonce 派生每条消息的 AES-128 CTR key。EID 会按字节序排序后参与派生，因此两端能得到相同 key。

这不是最终的非对称端到端加密，只是适合当前 B85 RAM/Flash 约束的过渡方案。

## 后续升级方向

正式产品安全方案建议升级为手机 App 侧的会话密钥协商：

1. 手机端生成短期密钥对。
2. 通过 B85 P2P 可靠通道交换公钥或握手消息。
3. 手机端完成 ECDH/密钥派生。
4. B85 只转发密文，不再持有聊天明文。

这样可以把“终端广播链路加密”升级成真正的端到端会话加密。
